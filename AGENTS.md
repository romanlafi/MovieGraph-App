# AGENTS.md — MovieGraph-App

## Mission

Refactor MovieGraph-App into a clean, maintainable, production-ready portfolio application for Cloudflare while preserving the current product behaviour.

The target platform is:

- React + TypeScript + Vite frontend
- FastAPI backend running as a Cloudflare Python Worker
- PostgreSQL hosted on Neon
- Cloudflare Hyperdrive between the Worker and Neon
- TMDB as the source of truth for public movie/person/catalogue data

The most important architectural rule is:

> TMDB owns catalogue data. MovieGraph owns social/user/application data.

Do not persist TMDB catalogue entities in Neon merely to cache or mirror TMDB.

The migration is a refactor, not a rewrite.

---

## Architecture invariant

### TMDB owns

Treat these as external catalogue data:

- movie titles
- release dates
- posters
- backdrops
- plots/overviews
- runtimes
- TMDB ratings
- genres as catalogue metadata
- actors
- directors
- credits
- collections/franchises
- biographies
- person profile images
- trending/popular/top-rated/latest catalogue lists
- TMDB search results
- TMDB recommendations/similar content when used

MovieGraph should normally reference these entities by TMDB IDs rather than duplicating them.

Examples:

- `tmdb_movie_id`
- `tmdb_person_id`
- `tmdb_genre_id`

### MovieGraph owns

Persist only application-specific data such as:

- users
- authentication data
- user profiles
- follows/followers
- comments
- likes/favourites
- watchlist or collection state if implemented by MovieGraph
- user ratings if implemented by MovieGraph
- user preferences
- recommendation state or scores generated by MovieGraph
- social/activity data
- moderation/application metadata
- timestamps and ownership relations

If an internal record relates to a movie, store the TMDB ID.

Example:

```text
comments
--------
id
user_id
tmdb_movie_id
text
created_at
```

Do not require a local `movies` row merely so a comment can reference a film.

## Preferred production request flow

Preferred architecture:

```text
Browser
  |
  v
Cloudflare Python Worker
  |
  +-- /api/tmdb/*  ------> TMDB
  |
  +-- /api/v1/*    ------> Hyperdrive ------> Neon PostgreSQL
  |
  +-- static React/Vite assets
```

The TMDB routes are a thin backend-for-frontend/proxy layer.

Important:

- `/api/tmdb/*` must not query Neon merely to serve catalogue data.
- `/api/tmdb/*` must not insert movies, people, collections, credits or genres into Neon as a side effect.
- `/api/v1/*` represents MovieGraph-owned state and may query Neon.
- A MovieGraph endpoint may reference `tmdb_movie_id` or `tmdb_person_id`.
- A composite endpoint may combine TMDB and MovieGraph data when that materially simplifies the UI, but persistence boundaries must remain clear.

Do not expose the TMDB application credential in the browser bundle.


Preserve useful structure instead of performing an aesthetic rewrite.

### Current persistence coupling that must be removed

The current `Movie` model mirrors TMDB fields including:

- `tmdb_id`
- title
- year
- poster
- release date
- runtime
- box office/revenue
- website
- plot
- TMDB rating
- trailer
- tagline
- backdrop
- origin country
- collection

The current `Person` model also mirrors TMDB person data.

The current movie service:

1. searches Postgres,
2. searches TMDB if local results are insufficient,
3. fetches full TMDB details,
4. creates a local `Movie`,
5. creates genres,
6. creates collection data,
7. creates people,
8. creates cast/director relations,
9. commits the imported catalogue to Postgres.

This entire catalogue-mirroring behaviour is a migration target.

The current relationships also couple MovieGraph-owned state to the mirrored catalogue:

- comments reference local `movies.id`
- likes reference local `movies.id`
- users have a relationship to locally persisted Movie rows
- catalogue relationships depend on local Movie/Person/Genre/Collection rows

Codex must migrate those relations safely to TMDB IDs before deleting obsolete catalogue tables.

## Read before changing anything

Before every substantial change:

1. Read this file.
2. Read `docs/CLOUDFLARE_MIGRATION.md`.
3. Inspect all affected models, routes, schemas, services and frontend callers.
4. Identify current user-visible behaviour.
5. Identify whether the data involved belongs to TMDB or MovieGraph.
6. Preserve behaviour unless the migration document explicitly changes it.
7. Make the smallest coherent change that advances the target architecture.
8. Run validation before moving to the next phase.

Never delete a table or model solely because it appears redundant. First trace all foreign keys, ORM relationships, schemas, services, tests and frontend consumers.

## Data ownership decision rule

Before creating a database column or model, ask:

> Would MovieGraph still own this value if TMDB disappeared tomorrow?

If the answer is no, it generally should not be persisted as authoritative MovieGraph state.

Good persisted values:

```text
user_id
tmdb_movie_id
liked_at
rating_by_user
comment_text
recommendation_score
status
created_at
updated_at
```

Bad catalogue mirror values unless explicitly justified:

```text
movie_title
movie_plot
poster_url
tmdb_vote_average
actor_biography
actor_photo
movie_runtime
collection_backdrop
```

Small denormalized snapshots may be allowed only when there is a concrete product requirement, such as immutable activity history. Document that exception.

## Database target

Neon PostgreSQL is the authoritative database for MovieGraph-owned state.

Cloudflare Hyperdrive is the production connection path from Worker to Neon.

Do not:

- expose Neon credentials to the browser
- persist TMDB catalogue purely as a cache
- create a second primary database such as D1
- use the database as a TMDB response cache
- run schema creation/migrations automatically on web requests

### Candidate final domain schema

The exact schema must be derived from current behaviour, but conceptually prefer relations such as:

```text
users
user_follows
comments(user_id, tmdb_movie_id, ...)
user_movie_likes(user_id, tmdb_movie_id, ...)
user_movie_state(user_id, tmdb_movie_id, ...)
user_genre_preferences(...)
recommendations(user_id, tmdb_movie_id, score, ...)
```

A dedicated `movies` table should not exist merely to mirror TMDB.

A dedicated `persons` table should not exist merely to mirror TMDB.

## Legacy catalogue tables

Current models that are candidates for removal after migration include:

- `movies`
- `persons`
- `movie_person`
- `collections`
- movie ↔ genre catalogue association tables
- other tables whose only purpose is reproducing TMDB catalogue structure

Do not remove them in the first step.

Required removal sequence:

1. inventory all references
2. add TMDB ID columns to MovieGraph-owned relations
3. backfill those IDs from existing catalogue rows
4. update code to use the new fields
5. verify behaviour
6. add constraints/indexes
7. stop writing catalogue rows
8. remove obsolete foreign keys/relationships
9. drop catalogue tables only in a later explicit migration

## Comments migration rule

Current comments reference `movies.id`.

Target:

```text
comments.tmdb_movie_id
```

Migration must preserve existing comments.

Conceptual migration:

```sql
ALTER TABLE comments ADD COLUMN tmdb_movie_id INTEGER;

UPDATE comments c
SET tmdb_movie_id = m.tmdb_id
FROM movies m
WHERE c.movie_id = m.id;
```

Then verify there are no null/unmapped rows before making the new field non-null and removing the old FK.

Do not blindly copy this SQL; adapt it to the real migration state.

---

## Likes migration rule

Current user/movie likes ultimately depend on local Movie rows.

Target relation:

```text
user_id
tmdb_movie_id
```

with a uniqueness constraint similar to:

```text
UNIQUE(user_id, tmdb_movie_id)
```

Preserve all existing likes during migration.

Do not require a local Movie row before a user can like a TMDB movie.

---

## Genres

There are two different concepts:

1. TMDB catalogue genres attached to a movie
2. MovieGraph user preference for genres

Do not keep a movie ↔ genre local catalogue graph just to mirror TMDB.

If users can persist favourite genres, that is MovieGraph state and may remain persisted.

Prefer storing a stable TMDB genre identifier for such preferences where appropriate.

Audit the current `Genre` model and association tables before deciding what stays.

---

## Recommendations

Treat recommendation logic carefully.

There may be two kinds of recommendations:

### TMDB recommendations

These belong to TMDB and should be fetched from TMDB without persisting the catalogue.

### MovieGraph recommendations

These belong to the application.

A MovieGraph recommendation may persist:

```text
user_id
tmdb_movie_id
score
reason/type
generated_at
```

It should not require a local full Movie row.

If the current recommendation algorithm relies on locally mirrored cast/genre/movie tables, refactor the algorithm deliberately rather than silently dropping behaviour.

Possible inputs can be fetched from TMDB and transformed in memory.

Do not confuse a TMDB recommendation response with a MovieGraph-generated recommendation.

## TMDB client rules

Create one coherent TMDB integration layer.

Suggested direction:

```text
back/app/services/tmdb/
  client.py
  movies.py
  people.py
  search.py
```

A smaller structure is fine if clearer.

Requirements:

- one source of TMDB base URL/authentication
- application credential only on the backend
- explicit timeout
- consistent error mapping
- query parameters validated
- no blocking chaos duplicated across route modules
- response transformation centralized where useful
- no database writes inside the TMDB client

Prefer using TMDB capabilities efficiently, including append/combined requests where supported and useful, rather than automatically issuing several sequential requests for every page.

Do not over-engineer a full SDK.

## Cloudflare runtime rules

Production backend runs as a Python Worker, not a traditional Linux server.

Do not assume:

- Uvicorn is running in production
- Docker exists in production
- localhost services exist
- a persistent writable filesystem exists
- a long-lived traditional process lifecycle exists
- arbitrary native CPython packages work

Use the currently supported Cloudflare Python Worker ASGI/FastAPI integration.

Use current official Cloudflare documentation as authority when implementation details differ from historical assumptions.

The Worker entrypoint should be minimal and separate from application construction where practical.

---

## Hyperdrive and SQLAlchemy

The current application uses synchronous SQLAlchemy.

Preserve synchronous SQLAlchemy if it remains supported and reliable for the current Cloudflare Python Worker runtime.

Do not convert the application to async SQLAlchemy merely for fashion.

Before changing drivers or connection construction:

1. verify current official Python Workers + Hyperdrive support
2. verify the selected Postgres driver works in Workers
3. verify SQLAlchemy integration
4. test SELECT
5. test INSERT/UPDATE/DELETE
6. test transaction rollback
7. test request-scoped session cleanup

Hyperdrive already handles connection pooling at the platform layer.

Avoid unnecessary aggressive application-side pooling.

---

## Database migrations

Use explicit schema migrations.

Preferred: Alembic if compatible with the project workflow.

Migrations must be executed from a trusted development/CI/admin environment, not automatically during Worker requests.

Data migrations removing the TMDB mirror are especially important.

Never drop:

- `movies`
- `persons`
- `collections`
- genre associations
- movie/person associations

until all MovieGraph-owned data has been backfilled to TMDB IDs and verified.

## API namespaces

Prefer a clear boundary:

```text
/api/tmdb/*
```

External catalogue gateway.

```text
/api/v1/*
```

MovieGraph application state.

Existing public paths may need temporary compatibility wrappers during migration.

Do not break the frontend and backend simultaneously without a coordinated change.

## Composite responses

It is acceptable for MovieGraph-owned endpoints to enrich data with TMDB when useful.

Example:

```text
GET /api/v1/users/{id}/likes
```

Neon may return:

```text
[550, 680, 155]
```

The backend or frontend may enrich those IDs with TMDB catalogue information.

Choose based on UX/network efficiency.

The invariant remains:

> The database stores the relationship, not the mirrored movie catalogue.

Avoid N+1 TMDB calls. Batch/parallelize/enrich intelligently where the API permits.

## Configuration

There must be one clear configuration strategy.

### Backend secrets

Examples:

```text
SECRET_KEY
TMDB_API_KEY or TMDB_READ_ACCESS_TOKEN
database/Hyperdrive runtime configuration
```

### Backend non-secret configuration

Examples:

```text
TMDB_BASE_URL
JWT_ALGORITHM
ACCESS_TOKEN_EXPIRE_MINUTES
APP_ENV
```

Do not use `VITE_*` variables for secrets.

Do not expose TMDB application credentials through the frontend.

Do not use `load_dotenv()` as the production configuration mechanism for Workers.

Local development may still use `.dev.vars`, local environment variables, or an explicitly documented equivalent.

---

## Authentication

Preserve current auth behaviour during infrastructure/catalogue migration unless explicitly tasked to redesign it.

Current frontend Bearer-token behaviour may remain temporarily.

Requirements:

- password hashing remains secure
- JWT secret stays server-side
- expiry is enforced
- authorization is checked server-side
- no secrets in logs
- authenticated identity should come from the token, not trusted client user IDs

Moving tokens from localStorage to HttpOnly cookies is a possible future improvement, not part of the catalogue migration unless explicitly requested.

---

## CORS

The current backend uses broad CORS.

Do not keep production:

```python
allow_origins=["*"]
allow_credentials=True
```

If static frontend and API use the same Worker/origin, prefer same-origin requests and remove unnecessary CORS.

For local development, configure only the origins actually required.

---

## Frontend rules

Keep:

- React
- TypeScript
- Vite
- current router unless a real problem exists
- a single API client strategy

Do not migrate frameworks during this refactor.

Frontend should stop depending on locally mirrored Movie/Person database IDs for catalogue navigation.

Use TMDB IDs for catalogue routes and UI state.

Example:

```text
/movie/550
/person/287
```

where those identifiers are TMDB identifiers.

Audit all frontend types and service methods that currently use ambiguous fields named only `id`.

Prefer explicit naming at boundaries:

```ts
tmdbId
tmdbMovieId
tmdbPersonId
userId
commentId
```

Avoid mixing internal database IDs and TMDB IDs.

---

## Frontend data flow

Preferred:

```text
search/details/catalogue
    -> /api/tmdb/*

comments/likes/follows/account
    -> /api/v1/*
```

For a movie detail page, parallel requests are acceptable:

```text
GET /api/tmdb/movie/550
GET /api/v1/movies/550/comments
GET /api/v1/movies/550/me
```

or a deliberate composite MovieGraph endpoint may combine them.

Do not reintroduce the old "fetch TMDB -> insert Movie -> return local Movie" behaviour.

## Static assets

Preferred production is one Cloudflare Worker serving:

- Python/FastAPI API
- React/Vite static assets

Same-origin deployment simplifies:

- CORS
- configuration
- API URLs
- portfolio deployment
- secrets

Use Workers Static Assets according to current official Cloudflare guidance.

Ensure SPA fallback never swallows `/api/*`.

## External caching

Do not use Neon as a TMDB cache.

Optional platform/HTTP caching may be introduced later if useful.

If adding cache:

- use HTTP/Cloudflare cache semantics
- define TTLs deliberately
- do not cache user-specific authenticated responses as public content
- do not introduce KV/D1/Durable Objects without a concrete reason

The first successful migration does not require a custom cache.

Prefer fewer dependencies.

Backend:

- remove `psycopg2-binary` if incompatible with the target Worker runtime
- keep only a Worker-compatible PostgreSQL driver
- Uvicorn is not a production runtime requirement under Workers
- retain local-only tools only if useful and clearly classified
- use `pyproject.toml` when appropriate for current Python Workers tooling

Frontend:

- keep npm unless a concrete reason exists to change
- avoid unrelated dependency churn

## Code quality

### Python

- modern SQLAlchemy 2.x style where practical
- type hints on meaningful boundaries
- explicit error handling
- no wildcard imports
- no broad silent exception swallowing
- no unnecessary global mutable state
- no DB writes hidden inside read-only TMDB helpers

### TypeScript

- avoid `any`
- explicit domain/API types
- distinguish TMDB IDs from internal IDs
- one API client strategy
- no duplicated domain interfaces without reason
- remove dead code only after proving it is unused

### General

- human-readable code over clever code
- comments explain why
- delete obsolete commented-out code
- do not generate boilerplate for its own sake
- simplify rather than accumulate parallel architectures

## Tests

Protect the migration with behavioural tests.

Backend should cover representative cases:

### Catalogue

- search does not write to Neon
- movie detail does not create a local Movie row
- person detail does not create a local Person row
- TMDB failure maps to sensible API error
- no TMDB credential is returned to client

### MovieGraph state

- registration/login
- follow/unfollow
- create/list/delete comment as currently supported
- comments use `tmdb_movie_id`
- like/unlike uses `tmdb_movie_id`
- duplicate likes are prevented
- existing migrated comments/likes remain accessible
- authorization rules remain intact

### Database migration

- every legacy comment with a valid local movie maps to a TMDB ID
- every legacy user/movie like maps to a TMDB ID
- no MovieGraph-owned records are orphaned before catalogue table removal

Frontend minimum validation:

```bash
npm run lint
npm run build
```

Add focused tests where they protect meaningful behaviour.

## Migration safety

Never combine all of these in one uncontrolled change:

- Cloudflare runtime migration
- Hyperdrive migration
- catalogue data model deletion
- frontend ID semantics
- auth redesign
- UI redesign

Move in phases.

During transitional phases it is acceptable to have compatibility code.

Temporary compatibility code must be labelled and removed later.

---

## Definition of done

The refactor is complete only when:

- FastAPI runs on Cloudflare Python Workers
- React/Vite is deployed successfully
- Hyperdrive connects the Worker to Neon
- Neon stores only MovieGraph-owned state plus justified exceptions
- search uses TMDB without first searching local Movie rows
- movie details use TMDB without persisting the movie
- person details use TMDB without persisting the person
- comments reference TMDB movie IDs
- likes/favourites reference TMDB movie IDs
- recommendation state does not depend on a mirrored full Movie row
- legacy catalogue rows/tables are safely migrated and removed where appropriate
- frontend consistently understands TMDB IDs versus internal IDs
- TMDB credentials remain backend-only
- CORS is production-safe
- core current features still work
- no production Docker/Uvicorn assumptions remain authoritative
- README documents the real architecture
- relevant lint/build/tests pass
